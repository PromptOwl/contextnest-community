Give the agent setup prompt failure branches, so a first read that fails is recoverable instead of terminal.

**Measured, not judged.** Five prompt variants, two runs each, fresh agents against a containerised 1.20.0 built from `origin/main`, reading a seeded nest. The server was unlicensed for the run — which is the state of every trial and every fresh self-host. Under identical conditions the variant that said "if it fails, stop" connected **0/2**; a minimal variant managed **1/2**, and that one success came from an agent improvising past the failure unaided; the variant that documented what to do when the first read fails connected **2/2 with full document text in two calls**. Telling an agent how to recover is the entire difference — nothing else in the copy came close.

So `nestSetupPrompt` now branches on what actually came back. **503** is the license gate on `POST /context`: `GET /export?format=markdown` is not gated and returns every document with its text in a single call, with list-then-read kept as the escape hatch for a nest too large to take whole. **401** means the key is wrong — ask, don't retry. **403** is split deliberately: a JSON error body is the server refusing you, usually a key scoped to another nest, which is fixable; a 403 with no body is a gateway, which is not. **No response at all** means the environment cannot reach the host — a sandbox or egress policy — so retrying and tunnelling are both pointless, and the answer is a custom connector, which is dialled server-side and isn't subject to the caller's egress rules. That last case came from a real cloud agent blocked by an allowlist, a failure mode the prompt previously had no concept of because it treated "has a shell" as meaning "can reach the internet".

**The key is now located rather than requested.** The old copy asked the agent to ask for the key while forbidding the key in chat, and named no other channel; four of ten runs stopped exactly there, one calling the task "unachievable as written". It names `CONTEXTNEST_API_KEY` — what the `.env` download already writes — and says plainly that an agent cannot mint one, because `/auth/keys` needs a signed-in session and the old "set it up yourself" promised something impossible.

**Write tools are named instead of asserted.** Told in prose that a connection "reads and writes", five of six agents still answered "unsure" about writing; the ones who were sure had seen a command or a field. So `context_create`, `context_update`, `context_move` and `context_submit_review` are named. For the same reason `push` is gone from this brief — it uploads a folder *into* a nest, a different job, and it was the direct cause of agents concluding the CLI is the only thing that can write. `ctx vault add` moves down beside MCP under "later, after a restart", leaving one live path instead of four.

Testing the rewrite the same way found two defects in it before it shipped: a bare slug 404s because the id the list returns already begins with `nodes/` and is appended whole, and `/search` needs a term so it cannot enumerate a nest. Both are now spelled out rather than left to inference, and the re-run came back 2/2 with full text and zero wrong turns.
